## Testing

- A fallback branch that no captured fixture reaches (`largest WT1 none`, `on no Worker` in the receipt-gap identity view) needs a history derived from a capture inside the test, with "derived" in the test name, and a temporary mutation of the branch to show the test can fail (2026-11-11)
- A test fake that reports a value read from the code under test cannot catch a wrong constant: the exercise 06 gate tests could not fail on `FREEZE_GATE_ACTIVITY` until the fake's pending activities named `get_ip` and `get_location` as literals; pin the expected literal in the test (2026-11-11)
- A branch that only runs when a sleep wakes late (the flood producer's late-wake rule) runs in no test under a fake sleep that returns on time; patch `monotonic` and `asyncio.sleep` with a virtual clock the fake sleep advances, script one late wake, and test both sides of the threshold (2026-11-11)
- A holder thread that sets a readiness `threading.Event` only after it takes the lock leaves the waiter blocked forever when the take fails (exercise 06 `CacheLock.__enter__` on a database it could not open); set the event in a `finally`, store the error, and have the waiter join the thread and raise it (2026-11-10)
- A test that checks for a hang must be bounded itself: run the blocking entry on a daemon thread and `join` it with a limit (5 s in `test_entering_a_lock_whose_database_cannot_be_opened_raises`), then assert the thread finished, so the bug fails the test instead of stalling the suite (2026-11-10)
- In the per-Worker panel test a count assertion ran before the no-`sum` assertion, so a `sum by (worker_type)` wrap failed with the count message and the summing message could never fire; order assertions from the most specific failure message to the least, and run the teeth check to see which message actually fires (2026-11-10)
- When a plan says a test runs against captures and no machine-readable capture exists, capture one live (`temporal workflow show --output json`) instead of reconstructing fixtures backward from the expected output; a fixture built to match the expected result makes a circular test. Step 15's first validator pass caught it (2026-11-08)
- pytest resolves a relative `pythonpath` ini value against the config file's directory, not the cwd, so a per-directory run from a subdirectory with `-o pythonpath=.` put the repo root on every copy's sys.path; pass an absolute path (`-o pythonpath="$PWD"`) inside the cd subshell to keep the repo root off it. Proved with throwaway two-copy probes (2026-11-03)
- A config test that must assert "exactly these values and nothing else" should scan for every token of the value's shape across the whole file rather than parse structure with regexes; structural regex parsing failed open across two validator rounds (2026-11-03)
- Config-file tests assert the stack's invariants (the service set, the scrape targets, the metric allowlist) and nothing else; "parses as YAML" and asserting a value we chose were rejected as testing for the sake of it (2026-11-03)
- Concurrent `execute_workflow` calls (`asyncio.gather`) under `WorkflowEnvironment.start_time_skipping()` can race the server's automatic clock advance against real workflow-task dispatch, producing spurious `START_TO_CLOSE` timeouts; wrap the `gather` in `env.auto_time_skipping_disabled()` (synchronous context manager) to remove the race (2026-09-23)
- An error-path test that asserts only the exception type does not prove a retry policy is disabled; record `activity.info().attempt` per invocation and assert the attempt count (`== [1]` for `maximum_attempts=1`) so the test fails if retries come back (2026-09-17)
- For timing-based probe tests, pick gap thresholds with wide slack in one pass (block 0.5 s against a 0.4 s floor, not 0.45 s); do not re-run the suite to tune thresholds to the edge, which invites flakiness and a hung tuning loop (2026-09-17)
- pytest exits 5 when it collects no tests, which fails a `just check` gate; give a freshly scaffolded package a single import smoke test rather than loosening the gate (2026-09-17)

## Temporal

- A Workflow Task that times out records no execution latency, so the Workflow Task Execution Latency panel cannot show a stall that a timeout carries: in one root `just block` run the receipts' 29-second first-task stall left their line empty, and the panel's only high reading (5.14 s) sat on the rollup line (one run, 2026-11-11)
- A flood B run read a backlog of 39 tasks aged 3.5 s and a frozen Worker's pollers 6 and 8 seconds stale only at the last of four mid-freeze passes (about 19 s in); the passes at about 0 and 2 s read backlog 0 and current pollers, so one early read does not show the signal is absent; take passes across the whole freeze and name the pass in the sentence (one run, 2026-11-11)
- An `ActivityTaskStarted` history event is written only when the Activity finishes, so a mid-freeze reading triggered on it falls after the thaw (two of four exercise 06 flood B runs); trigger on the starter's own output or on the pending Activity state from `describe` (2026-11-11)
- A history fixture attributes a WorkflowTaskTimedOut through the scheduled event id it shares with a WorkflowTaskStarted, because the timeout event carries no identity; a timeout with no Started event belongs to no identity (2026-11-11)
- After the `def` plus executor fix, a two-Worker flood with a 30-second `sqlite3` lock wait failed no receipt and timed out no Workflow Task in five of six runs (median 0.33 to 0.40 s, slowest 0.55 to 1.25 s); the lookup waits on a `ThreadPoolExecutor` thread and both main threads sit in the selector (2026-11-10)
- One after-fix flood was slow with no failure (260 of 528 receipts over 2 s, one Workflow Task timeout): it was the fourth of five back-to-back floods on one dev server with process tools attached, and the next flood on that server was clean; the cause is unknown, so start a fresh dev server for each capture flood and never quote one run as the result (2026-11-10)
- The query `temporal_worker_task_slots_used{worker_type="WorkflowWorker"}` also returns six all-zero series from the dev server's own system Workers when Prometheus scrapes the server's metrics port; add `task_queue="async-debug-task-queue"` to get one line per Worker (2026-11-10)
- Two Activities on two Workers do not reliably split one per Worker: both ran on one Worker in two of two saved invocations, after an earlier inference from durations alone said one each; save the per-identity printout, and fill every slot (four runs) when a step depends on placement (2026-11-10)
- With two Workers at 2 Activity slots each, no receipt failed at any burst size (8, 100, 500); at the SDK default of 100 slots under steady traffic of 10 receipts per second, 17 to 22 of about 515 failed (3.3 to 4.3 percent) in six freeze runs. A demo's small slot count can hide the fleet symptom, so run a fleet exercise at the default slot counts (2026-11-10)
- A burst is the wrong load for showing a partial failure: 500 receipts at once overloaded the healthy Worker (median 14.0 s) and no receipt failed, and at default slots the result swung with burst size (1 of 8, 27 of 100, 0 of 500), while steady traffic failed 3.3 to 4.3 percent in each of six runs. Run the same steady rate with no bad Workflow as the control (0 of 521 failed, slowest 0.90 s) so a reader can tell the bug from the load (2026-11-10)
- With a healthy Worker on the same Task Queue, `temporal task-queue describe` read backlog 0 and age 0 in every single mid-freeze read, and a 2-second sampler saw only brief backlogs (1 to 4 tasks, under 0.3 s old, in three of five flood runs), so the single-Worker backlog signal is gone. What still separates the frozen process: its `WorkflowWorker` `temporal_worker_task_slots_used` gauge climbs (31 of 100 early, 95 or 96 at its peak) while the healthy one stays low (peaks of 3 to 6), and `py-spy dump` and `asyncio pstree` read each PID as before. The `ActivityWorker` gauge does not separate them (2026-11-10)
- A retried Activity leaves one `ActivityTaskStarted` in history, written for the last attempt with its `attempt` number; earlier attempts leave no event. Counting Activity attempts per Worker identity from history therefore sees final attempts only, and the frozen Worker's log ("Task not found when completing") is where the swallowed attempts show (2026-11-10)
- A second Worker on the same Task Queue hides a frozen Worker's failures: in five two-Worker freeze runs no bystander failed, the frozen Worker still took half the first Workflow Tasks, and the stalls came in 10-second steps as retries landed on either Worker. Spike a fleet exercise's symptom before writing its capture requirements; the spec's assumed "one rollup fails" was wrong (2026-11-09)
- After a `WorkflowTaskTimedOut`, the server writes no history events for the retries in between; the next `WorkflowTaskScheduled` in history carries `attempt` 2 or 3 and is the attempt that completed. `WorkflowTaskTimedOut` has no identity, so attribute it to the `WorkflowTaskStarted` before it (2026-11-09)
- A starter gate that scrapes one Worker's metrics port breaks as soon as a second Worker shares the Task Queue (in one of five runs it waited its full timeout because the rollup's Activity ran on the other Worker); gate on the server's `describe()` so the check does not depend on which Worker took the task (2026-11-09)
- The Temporal Python SDK reports latency histograms in milliseconds, so a Grafana panel with unit "s" misreads by 1000x; check the unit against a live scrape before trusting a panel (2026-11-03)
- A frozen event loop fails no worker-side activity, so worker failure counters stay empty; plot the dev server's `activity_timeout` series as the failure signal (2026-11-03)
- A retried activity writes no history event per failed attempt; the failed attempts show in the Web UI pending-activity view, `temporal workflow describe` (Attempt, LastFailure), and the Worker log, so a retry storm is visible without history events and needs UI screenshots in the captures (2026-11-08)
- Spreading CPU-bound runs across Worker processes needs a free slot on each process, or the server can place both runs on one and the second Worker adds nothing (2026-11-03)
- Moving pure-Python CPU work to a thread unblocks the event loop (the probe test is green, no asyncio debug-mode warning) but does not restore bystander latency, because the thread still holds the GIL against the workflow-task thread (receipts' first workflow task stayed at 357 to 617 ms). A "short blocker" example that a thread fixes needs GIL-releasing C work (one large `zlib.compress` or `hashlib` call over prebuilt bytes: practice 267 to 345 ms, solution 18 to 49 ms), and recovery must be measured live, since a probe test alone passes either way (2026-11-03)
- An `async def` activity that `time.sleep`s in a loop without ever awaiting produces one Heartbeat timeout plus a zombie that holds the loop until it finishes, not a retry storm, because the retry cannot run Python until the loop thaws; reasoning about retry timing on a frozen loop needs a live capture (it was wrong here in spec.md and plan.md) (2026-11-03)
- In the Python SDK, `activity.heartbeat()` inside an `async def` Activity schedules an asyncio task to send the heartbeat, so a heartbeat recorded right before `time.sleep` cannot leave the Worker until the sleep ends; the "time.sleep between heartbeats" bug therefore only trips the heartbeat timeout when one sleep exceeds it, and the one-line `await asyncio.sleep(same_interval)` is not a fix (still no heartbeat for that long). The fix is awaited short ticks with a heartbeat per tick. Reasoned from the SDK, to be confirmed by the Step 10 capture (2026-11-03)
- When a demo workflow runs several activities that each block the loop, the loop is live for only ~100ms between them, so anything released at an intermediate thaw can race the re-freeze; gate on the LAST freezing activity reporting STARTED (describe()'s pending_activities carries activity_type and state), not the first (2026-10-07)
- To demo slot exhaustion without a race, fill the slots first and confirm it: submit the slot-holders, poll temporal_worker_task_slots_available until the ActivityWorker gauge reads 0, then submit the work that should starve, so it fails on schedule_to_start every run (2026-09-18)
- To gate on "the Worker has started running Activity X" from outside the Worker, poll the Workflow handle's describe() for a pending activity in PendingActivityState.STARTED; temporal_worker_task_slots_available cannot identify which Activity holds a permit, and a frozen Worker cannot block a client-to-server describe() call (2026-10-07)
- `maximum_attempts=1` gives at-most-one dispatch, not exactly-once: a transient failure before the call means the operation never runs, and a Worker that finishes the side effect but crashes before recording it leaves the effect done while the Workflow sees failure; effectively-once comes from keeping retries plus an idempotent Activity keyed on workflow_run_id + activity_id (per docs.temporal.io fixed-count-retries and the multi-cluster guide) (2026-10-04)
- Do not set non_retryable on an ApplicationError raised inside Workflow code; any ApplicationError from the Workflow already fails the run, and a plain ValueError there only fails the workflow task, which the server retries forever (the run stalls instead of failing) (2026-10-04)
- The Temporal Python SDK serves its Prometheus metrics endpoint from the Rust core runtime on its own threads, not the Python event loop, so `curl :9464/metrics` stays reachable while a blocking call freezes the loop (verified live). The frozen-loop signal is the `asyncio ps` SHAPE (the wedged task dead-ended at `_ActivityWorker._handle_start_activity_task`, every other task parked at an await) plus CPU, with `py-spy dump` for the exact line, not endpoint reachability (2026-10-04)
- Python 3.14 `asyncio ps` / `pstree` do NOT show an async activity's blocking line when it is wedged in synchronous code; the task truncates at the SDK frame `_ActivityWorker._handle_start_activity_task` because asyncio walks the await chain and sync code is not an await. `py-spy dump` shows the real thread stack down to the `time.sleep` call site; asyncio ps still distinguishes the culprit (dead-ended, no await beneath) from healthy tasks (parked at awaits) (2026-10-04)
- A Temporal Python worker's pollers live in the Rust core and keep long-polling through a frozen event loop, so poller `LastAccessTime` in `temporal task-queue describe` is not a freeze signal (it stays inside the idle 0-59s cycle and the worker never leaves the Pollers list); during slot saturation its age grows only while no activity permit is free, a weak hint at best. The live saturation tell is the activity backlog age read together with a healthy `asyncio ps` shape (every task parked at an await, none dead-ended), since a backlog under a dead-ended task is a freeze, and `temporal_activity_schedule_to_start_latency` only moves once a queued task finally starts (2026-10-07)
- A never-started activity with only schedule_to_close set times out labeled ScheduleToStart, because the server copies schedule_to_close into schedule_to_start when the latter is unset (2026-10-07)
- To hold an activity slot for a long cooperative wait, heartbeat every few seconds inside the wait (interval a few times shorter than heartbeat_timeout); otherwise the server cancels the activity at heartbeat_timeout and frees the slot early (2026-09-18)
- Test an activity's heartbeat ordering by assigning `ActivityEnvironment.on_heartbeat`; it receives the same `*details` the activity passed to `activity.heartbeat`, so no worker needs to run (2026-09-17)
- `schedule_to_start_timeout` is non-retryable and normally an antipattern; it is useful in demos precisely because it converts slot exhaustion into a fast, visible failure (2026-09-16)
- `schedule_to_start_timeout` combined with `WorkflowEnvironment.start_time_skipping` is flaky because the skipped clock can cross the deadline while tasks queue; test such workflows under a real-time (`start_local`) environment (2026-09-17)
- A cooperative slow-mode Activity that awaits `asyncio.sleep` without heartbeating gets cancelled at its `heartbeat_timeout` (10s here), not at the full sleep duration, so a slot-exhaustion window built on `--block-seconds 30` is really only ~10-14s wide; to hold slots for the full duration, heartbeat periodically during the wait or lengthen the heartbeat timeout (2026-09-18)
- When a shared helper is called both inside and outside an activity (e.g. reused by a Temporal-free test), guard activity.heartbeat with activity.in_activity() so the bare call does not raise (2026-09-18)
